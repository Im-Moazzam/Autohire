# US-15 + US-16: Trigger AI processing and extract resume text

- **Status:** Done
- **Epic:** EP-04
- **Points:** 13
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-12, US-13

> Planned as one story because they share all the Celery infrastructure. **Build as two
> commits:** (1) task plumbing + `background_tasks` + status endpoint, (2) extraction
> and `PARSE_ERROR` handling.

## Story
As a recruiter, I want to start processing the resumes I've collected and watch it
progress, so that I know when the shortlist is ready and which resumes failed.

## What this story is
The first asynchronous work in the system, and the first genuinely unpredictable
story — extraction quality across real, messy resumes is the variable you can't
estimate. Routes exist as TS-02 stubs (`POST /jobs/{job_id}/process`,
`GET /jobs/{job_id}/process/status`).

Embeddings and scoring are **US-18** and are not in this story. This story ends with
extracted text sitting in the database and failures visible.

## Commit 1 — task plumbing

### Acceptance criteria
- [x] Migration creates `background_tasks` per `docs/schema.md`, plus
      `task_type_enum` and `task_status_enum`
- [x] The `background_tasks` row is written **on enqueue, not on worker start** —
      `architecture.md` is explicit: a worker that dies before picking up the job must
      still leave a trace
- [x] `POST /jobs/{job_id}/process` returns `TaskOut` 202 and enqueues one task
- [x] Re-triggering while a task for that job is `PENDING` or `RUNNING` → **409
      `PROCESSING_IN_PROGRESS`**, not a second task
- [x] Every task takes an idempotency key and is safe to run twice
- [x] `acks_late=True`, `max_retries=3`, exponential backoff, `soft_time_limit` set
- [x] Celery tasks open their **own** DB session — never one passed in from a request
      (same rule as `google_call`)
- [x] `GET /jobs/{job_id}/process/status` returns `ProcessStatusOut` with `total`,
      `processed`, `failed`, computed from candidate rows, not from task state
- [x] Triggering on a job with zero candidates → 409, no task
- [x] Tests run tasks eagerly (`task_always_eager`) — no live worker in CI

## Commit 2 — extraction

### Acceptance criteria
- [x] `app/services/resume_parser.py` — `extract_text(content: bytes, ext: str) -> str`,
      pypdf for PDF, python-docx for DOCX
- [x] Extracted text is persisted; add the column in this story's migration if
      `docs/schema.md` has no home for it, and log a `drift.md` row
- [x] Candidate moves `SUBMITTED` → `PARSED` on success
- [x] **A failed resume marks that one candidate `PARSE_ERROR` with a human-readable
      `parse_error`, and the batch continues.** One bad PDF must never abort a
      200-candidate run. This is the single most important AC in the story.
- [x] A resume that extracts fewer than ~50 characters (scanned image, empty) is
      `PARSE_ERROR` with a distinct message — not silently treated as an empty resume
      that then ranks bottom in US-18
- [x] OCR is **out of scope**; scanned PDFs are an honest `PARSE_ERROR`. Log in `drift.md`
- [x] Re-running processing retries only `SUBMITTED` and `PARSE_ERROR` candidates,
      not ones already `PARSED`
- [x] Extraction reads the file through `ResumeStore`, not by opening a path directly —
      add `fetch_resume(...)` to the Protocol if needed

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Trigger on a job with 5 candidates | 202, one `background_tasks` row, status PENDING |
| TC-02 | Trigger twice in a row | Second is 409, still one task |
| TC-03 | Trigger on a job with no candidates | 409, no task |
| TC-04 | Task runs, all resumes valid | All `PARSED`, `processed` = 5, `failed` = 0 |
| TC-05 | One corrupt PDF among five | That one `PARSE_ERROR` with a message; **other four PARSED**; `failed` = 1 |
| TC-06 | Task raises unexpectedly | `background_tasks.status = FAILED`, `error_message` set, candidates not left mid-state |
| TC-07 | Same task executed twice (idempotency) | No duplicate work, no double-counting |
| TC-08 | Scanned/image-only PDF | `PARSE_ERROR`, distinct message, not empty-string success |
| TC-09 | Re-trigger after a partial failure | Only the `PARSE_ERROR` candidate is retried |
| TC-10 | Status endpoint mid-run | `total`/`processed`/`failed` consistent, sums correctly |
| TC-11 | Cross-tenant trigger | 404 |

TC-05 is the one that matters. Write it first.

## Test fixtures — get these ready before starting
You need real resume files: a normal PDF, a DOCX, a scanned image-only PDF, a
corrupt/truncated PDF, and a password-protected PDF. Synthetic files will pass tests
while telling you nothing about real extraction quality. Put them in
`backend/tests/fixtures/resumes/`.

## Out of scope
Embeddings, vectors, scoring, ranking (US-18/19). LLM cleaning or structuring — that's
part of US-18's pipeline, not this one. OCR. Frontend progress UI — Saif owns it, but
the `processed`/`failed` split is the contract he builds the partial-failure view on.

## Note
`docs/checklists/ux.md` cares most about partial failure, and this is where it
originates. If three resumes fail, the ranking table in US-19 must show the successes
*and* surface the failures. The data model for that starts here — `failed` is a
first-class count, not an absence.
