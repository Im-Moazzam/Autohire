## Rules of engagement — read before touching anything

1. **Verify before you fix.** Every item has a **Repro**. Run it first.
   - Reproduces as described → fix it.
   - Does **not** reproduce → **change nothing.** Tick as `[~] NOT REPRODUCED`, record
     what you actually observed, move on. A fix for a non-existent bug is a regression
     with extra steps.
   - Reproduces *differently* → stop, record the real behaviour, flag it. Do not
     silently redefine the item.
2. **Regression test first.** Write the failing test *before* the fix. Show red, then
   green. The test is as much the deliverable as the fix.
3. **One commit per item**, `fix(TS-06/R-0X): <what changed>`. A not-reproduced item
   gets no commit.
4. **No unrequested refactors.** Spot something new → add it to the summary under
   *New findings*, do not fix it.
5. **Do not touch** `frontend/src/pages/{Apply,TemplateBuilder,Templates,Home}.tsx` or
   anything under `frontend/src/components/`. R-01 and R-08 touch
   `frontend/src/lib/jobs.ts` and `frontend/src/pages/Jobs.tsx` only.
6. **`api.d.ts` changes in this story, deliberately** (R-05/R-06/R-07). That is a
   recorded contract change, not drift. Run `make api-client`, commit
   `docs/openapi.json` and `frontend/src/lib/api.d.ts` **in the same commit as the
   route change**, confirm `npx tsc --noEmit` still passes. Never hand-edit either.
7. **Green gate before every commit:** `ruff check backend`, `mypy --config-file
   backend/pyproject.toml backend/app`, `pytest`. Baseline is **189 passed, ruff
   clean, mypy clean, 91% coverage**. Coverage must not drop.

## Items

### R-01 — `canProcess` gate makes AI processing unreachable from the UI  🔴

`frontend/src/pages/Jobs.tsx` enables "AI process" only when `job.status === "LIVE"`.
`task_service.enqueue_resume_parse` rejects anything not `CLOSED`. The button is
enabled exactly when the backend refuses, and greyed out with *"Only live jobs can be
processed"* exactly when it would accept.

**Repro (backend):** LIVE job with ≥1 submission → `POST /api/v1/jobs/{id}/process`
→ expect `409 INVALID_STATE_TRANSITION` ("Job must be CLOSED with candidates to
process.").
**Repro (frontend):** read `Jobs.tsx`; confirm `canProcess` requires `"LIVE"` and the
disabled tooltip states the opposite of what the backend enforces.

**Fix:** extract the gate into a pure exported helper in `frontend/src/lib/jobs.ts`,
`canProcessJob(job): { allowed: boolean; reason?: string }`. Correct rule: allowed when
`status === "CLOSED"` **and** `submission_count > 0`. Rewrite the tooltip to match
reality. `Jobs.tsx` calls the helper; no other behaviour change. Then confirm the flow
is completable: `Jobs` → *View / Edit* → *Close job* → back → *AI process* enabled.
`JobBuilder` already has Close — verify it, do not rebuild it.

**Prove it:** new `frontend/src/lib/jobs.test.ts` covering LIVE+n → false,
CLOSED+n → true, CLOSED+0 → false, DRAFT → false.

### R-02 — Parse retry impossible once a job is `PROCESSED`  🔴

`batch_ranking` sets `job.status = PROCESSED`. `enqueue_resume_parse` requires exactly
`CLOSED`; `enqueue_batch_ranking` accepts `(CLOSED, PROCESSED)`. Any candidate left in
`PARSE_ERROR` after a rank run can never be retried.

**Repro:** close → `POST /process` (202) → `POST /rank` (202) → job is `PROCESSED` →
`POST /process` again → `409 INVALID_STATE_TRANSITION`.

**Fix:** widen the guard to `job.status not in (JobStatus.CLOSED,
JobStatus.PROCESSED)`, mirroring `enqueue_batch_ranking`; update `_INVALID_STATE`'s
message. Safe because `_process_job_candidates` already filters to
`{SUBMITTED, PARSE_ERROR}` and `candidate_service._LEGAL_TRANSITIONS` forbids
`PARSED → PARSED`.

**Prove it:** a `PROCESSED` job with one `PARSE_ERROR` candidate accepts `POST
/process` and that candidate reaches `PARSED`; a `RANKED` candidate in the same run is
untouched.

### R-03 — `.doc` is advertised, accepted, and always fails parsing  🔴

`sniff_extension` returns `"doc"` for OLE2 magic. `extract_text` handles only `pdf` and
`docx` and raises `ExtractionFailed("unsupported file type for extraction: doc")`.
`Apply.tsx` advertises `accept=".pdf,.doc,.docx"`. A candidate uploading a Word 97 file
gets a success page and is silently unrankable.

**Repro:** POST a body starting `d0 cf 11 e0 a1 b1 1a e1` to
`/api/v1/public/apply/{slug}` → `201`. Close + process → that candidate is
`PARSE_ERROR` with `parse_error == "unsupported file type for extraction: doc"`.

**Fix:** reject where the candidate can still act. Remove the `_OLE_MAGIC` branch from
`sniff_extension` → `415 UNSUPPORTED_FILE_TYPE` at upload. Keep `_OLE_MAGIC` defined
with a comment on why it is recognised but not accepted. Consistency sweep — all must
agree `doc` is unsupported:
- `Apply.tsx` `accept` → `.pdf,.docx` *(the one permitted edit to that file)*
- `_MIME_BY_EXT` in `app/adapters/resume_store.py` and `app/api/routes/candidates.py`
- the 415 message in `candidate_service.submit_application` ("Only PDF, DOC, and DOCX
  resumes are accepted") → correct it

**Prove it:** OLE2 payload → `415`; `sniff_extension` returns `None` for it. Update any
existing test asserting `doc` is accepted.

### R-04 — `PATCH /interviews/{slot_id}` 404s on real slots; `POST /emails/send` returns a stale fixture  🔴

Both still read `app/api/fixtures.py`. `GET /interviews` returns real rows but `PATCH`
on one of those `slot_id`s → `404 SLOT_NOT_FOUND`. `POST /emails/send` returns
`fixtures.TASKS[TASK_RUNNING_ID]` — `task_type: BATCH_RANKING`, `status: RUNNING`,
`started_at: 2026-08-12T08:58:00Z` — whose `task_id` 404s at `GET /tasks/{id}`,
contradicting ADR-004 P4 and drift row 56.

**Repro:** schedule interviews → `GET /interviews` → take a real `slot_id` → `PATCH` →
`404`. Separately `POST /emails/send` → note the fixture body →
`GET /tasks/{returned_task_id}` → `404`.

**Fix:** both are genuinely Phase 2. Make them honest, do not implement them.
- Each raises `HTTPException(501, detail={"code": "NOT_IMPLEMENTED", "message": "<what
  it will do> is Phase 2 and is not implemented."})`.
- Keep the declared `response_model` and success status so the Phase 2 implementation
  does not change the shape twice. Add `501` to each `error_responses(...)`.
- Delete the unreachable fixture reads: `_to_slot_out` in `routes/interviews.py`, the
  `fixtures` import in both route modules, and any `fixtures.py` entry with no
  remaining caller. Run a dead-code check on `fixtures.py` afterwards; if nothing
  imports it at all, report that but do not delete the file in this story.

**Prove it:** `501 NOT_IMPLEMENTED` on both, plus a test that every 202 the app can
actually issue carries a `task_id` present in `background_tasks`.

### R-05 — Two authenticated routes do not declare 401  🟡

`GET /auth/me` and `PATCH /recruiters/me` depend on `get_current_recruiter` but declare
only `['422']`. Every other authenticated route declares 401.
`frontend/src/lib/auth.ts` catches `err.status === 401` from `/auth/me` — a branch the
generated types say is impossible. The session gate rests on it.

**Repro:** `python -m app.scripts.dump_openapi`, inspect `responses` for both
operations, confirm 401 absent; confirm unauthenticated `GET /auth/me` returns 401 at
runtime.

**Fix:** add `responses=error_responses(401)` to both. Regenerate the client (rule 6).

### R-06 — Job routes declare 502 but not the 500 they raise locally  🟡

`job_service.finalize_launch` raises **500** `RESUME_FOLDER_FAILED` when
`APP_ENV=local`, 502 otherwise. `POST /jobs` and `PATCH /jobs/{id}` declare only 502 —
the undeclared status is the one the demo config hits. `POST /public/apply/{slug}`
already declares both; match it.

**Repro:** read `finalize_launch`'s status-code branch, confirm both job routes omit
500 from `responses`.

**Fix:** add `500` to `error_responses(...)` on both. Regenerate. No behaviour change.

### R-07 — `JobUpdate` accepts a past `expires_at`; `JobCreate` does not  🟡

`JobCreate` has `_expires_in_future`; `JobUpdate` has none. A PATCH with a past
`expires_at` returns 200, leaves `status` as `LIVE`, and the public endpoint
immediately returns `410 JOB_CLOSED` while the recruiter's list still says LIVE.

**Repro:** `PATCH /jobs/{id}` with `expires_at` one day past → `200`,
`status: "LIVE"`. Then `GET /public/apply/{slug}` → `410 JOB_CLOSED`.

**Fix:** apply the same validator to `JobUpdate.expires_at`, skipping `None`. Factor it
so both schemas share one implementation. Do **not** change `assert_job_accepting` —
leaving an expired job `LIVE` is a deliberate US-06 decision (US-08 owns that
transition).

### R-08 — `expiresAtToDateInput` mixes UTC and local dates  🟡

`JobBuilder.tsx`: `dateToExpiresAt` builds from **local** `23:59:59`;
`expiresAtToDateInput` does `iso.slice(0, 10)` — the **UTC** date. Harmless at UTC+5,
but at a negative offset, opening and re-saving the edit form walks the deadline
forward one day per save.

**Repro:** a reasoning defect, not a runtime one at your offset. Verify by writing the
test below and watching it fail under `TZ=America/New_York`.

**Fix:** derive the date input from the local calendar date of the parsed instant
(`toLocaleDateString("en-CA")` or explicit local `get*()` calls), not a string slice.
Move both helpers into `frontend/src/lib/jobs.ts` so they are testable.

**Prove it:** round-trip test asserted under at least one negative-offset TZ.

### R-10 — `calendar_sync` fetches candidates without job or soft-delete scoping  🟡

`_run_calendar_sync` selects by `candidate_id.in_(...)` only — no `job_id`, no
`deleted_at IS NULL`. Enqueue validated both, but a candidate soft-deleted between
enqueue and execution would still be scheduled and emailed. Separately, on
`IntegrityError` the reason is hard-coded `"ALREADY_SCHEDULED"`, but
`uq_interview_slots_recruiter_time` can also raise it — the reported reason would be
wrong.

**Repro:** read the query, confirm both predicates missing. Confirm both partial unique
indexes exist in `e6f7a8b9c0d1_create_interview_slots.py` and that only one reason
string is ever emitted.

**Fix:** add `Candidate.job_id == job.job_id` and `Candidate.deleted_at.is_(None)`; an
excluded candidate falls into the existing `CANDIDATE_NOT_FOUND` branch. Inspect the
`IntegrityError`'s constraint name and emit `"ALREADY_SCHEDULED"` for
`uq_interview_slots_candidate_live` vs `"SLOT_TIME_TAKEN"` for
`uq_interview_slots_recruiter_time`, falling back to `"ALREADY_SCHEDULED"` if the name
is unrecoverable. Document the new reason in `docs/api-contract.md`'s `result_summary`
description.
