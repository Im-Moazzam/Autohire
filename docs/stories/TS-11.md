## Why this exists

Requested directly (not from the RS/SDS baseline — there is no mobile use case in the
original design). A recruiter-facing companion app: check jobs, candidates, interviews,
and emails from a phone. **No backend changes** — same FastAPI, same DB, same auth, same
routes as `frontend/`. See `mobile/README.md` for the technical setup and architecture
in full; this file is scope/acceptance-criteria, not a rebuild of that doc.

## Scope decisions (read before adding a screen or action)

**Screens:** Dashboard, Jobs (list + detail), Candidates (per job, list + detail),
Scheduling (view-only), Emails (view-only). No Templates, no Settings, no job
creation/editing — those stay authoring-only tools on the web app.

**Actions (only these two — everything else is read-only):**
- Reject / undo-rejection on a candidate (`PATCH /candidates/{id}`, same endpoint the web
  Candidates screen uses).
- Copy a job's application link (`apply_url`, already on `JobOut`/`JobDetailOut` — no API
  call at all, just clipboard).

**Why Scheduling has no confirm/cancel action:** `PATCH /interviews/{slot_id}` is a
deliberate backend stub that always 501s (`backend/app/api/routes/interviews.py`,
commented "Phase 2, not implemented"). The web Scheduling screen doesn't expose this
either — don't add it here without building the real endpoint first.

## Architecture worth knowing before you touch auth

The obvious approach — a native cookie-manager package reading the httponly session
cookie out of the login WebView — **does not work in Expo Go**. Expo Go's app binary
only ships the Expo SDK's own native modules; any third-party native module (like a
cookie manager) isn't in it and crashes instantly on import on a real device. This was
tried and reverted; see `mobile/lib/webviewBridge.tsx` for what's there instead: a
second, invisible, persistent WebView on the API's origin, whose page-context `fetch()`
carries the httponly cookie automatically (same as a real browser tab) — no native code,
no backend change, works in plain Expo Go. Read that file's top comment before changing
anything auth-related.

## Acceptance criteria

- [x] `EXPO_PUBLIC_API_HOST`-configured, LAN-IP-based API access (`mobile/.env`, gitignored;
      `.env.example` has placeholder only) — no hardcoded IP in source.
- [x] Google sign-in reuses the exact web OAuth flow via an in-app WebView; no separate
      mobile auth endpoint.
- [x] Every screen's data comes from the same endpoints the web app already uses — no new
      backend routes.
- [ ] All five UX states (loading/empty/error/partial/success) verified on each screen
      against real seeded data on a physical device — done for Dashboard and Login;
      Jobs/Candidates/Scheduling/Emails need an on-device pass.

      2026-09-08) — needs a real pass on spacing/hierarchy/polish, not just tokens wired
      up correctly.

## Notes

- Design tokens are hand-copied from `docs/design.md`/`frontend/src/styles/tokens.css`
  into `mobile/tailwind.config.js` (NativeWind) — keep in sync by hand until there's a
  shared tokens package. No mobile Figma file exists; layout is native-first (bottom
  tabs, drill-down stacks), not a port of the web app shell.
- `mobile/lib/api.d.ts` is generated from the same OpenAPI spec as the web client —
  `make api-client` now regenerates both together.
- Real bugs hit and fixed while building this (in case they resurface): NativeWind's
  `darkMode: "media"` crashes on `react-native-web` (fixed via `darkMode: "class"` in
  `tailwind.config.js`); `babel-preset-expo` and `react-native-worklets` need to be
  explicit dependencies or Metro can't resolve them after certain install orders.

## Out of scope

- Push notifications, offline support, biometric unlock — none requested.
- Any write action beyond the two listed above.
- A development build / EAS build — this deliberately stays Expo-Go-compatible.
