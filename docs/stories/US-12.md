# US-12: Candidate submits an application with a resume

- **Status:** Done
- **Epic:** EP-03
- **Points:** 13
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-06, US-11

## Story
As a candidate, I want to fill in the form and upload my resume, so that I am
considered for the job — without signing in to anything.

## What this story is
The second half of the public surface, and the **largest attack surface in the
system**: unauthenticated, accepts file uploads, writes to the database, and pushes
bytes into the recruiter's Google Drive. Treat every input as hostile.

Brings the `candidates` and `candidate_form_responses` tables, and adds
`store_resume(...)` to the `ResumeStore` Protocol built in US-06.

## Acceptance criteria

**Persistence**
- [x] Migration creates `candidates` and `candidate_form_responses` per
      `docs/schema.md`, including `submission_status_enum` (with `PARSE_ERROR`),
      UNIQUE `(job_id, email)`, and UNIQUE `(candidate_id, field_id)`
- [x] `POST /apply/{apply_slug}` accepts multipart: a `resume` file plus one value per
      template field
- [x] Reuses `job_service`'s acceptance check from US-11 — the same single function,
      not a copy. 404 / 410 behave exactly as in US-11.
- [x] All required template fields must be present and non-empty → 422 otherwise
- [x] A field id not belonging to this job's template → 422 (no writing arbitrary rows)
- [x] Duplicate `(job_id, email)` → **409 `DUPLICATE_SUBMISSION`**, no partial write
- [x] `submission_status` starts at `SUBMITTED`

**Upload**
- [x] `ResumeStore` gains `store_resume(recruiter, job, filename, content) -> StoredFile`
      returning the storage key plus (cloud) the Drive file id and URL
- [x] Local mode writes under `LOCAL_STORAGE_ROOT/resumes/{job_id}/`; cloud mode
      uploads into the job's Drive folder **via `google_call`**
- [x] **Ordering, as in US-06:** the resume is stored *first*, then the candidate row
      commits with the resulting key. A DB failure must not leave a candidate row
      pointing at a file that doesn't exist.
- [x] Storage failure → 502 (cloud) / 500 (local), no candidate row created
- [x] The stored filename is server-generated (UUID + validated extension), never the
      candidate's raw filename — path traversal and overwrite protection

**Validation — this is the security-critical part**
- [x] Accept only `.pdf`, `.docx`, `.doc`; reject everything else with **415** (amended
      from 422 — `docs/drift.md` row 33)
- [x] Validate by **magic bytes**, not the extension or the client's `Content-Type` —
      both are attacker-controlled
- [x] Hard size cap (**5 MB**, amended from 10 MB — `docs/drift.md` row 32), enforced by
      **streaming/counting as it reads**, not by trusting the `Content-Length` header
- [x] Empty file (0 bytes) → 422
- [x] `email` validated as an email address
- [x] Free-text responses length-capped (`response_value` is TEXT — cap in Pydantic)

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Valid submission, all fields, valid PDF | 201, candidate + response rows, file on disk |
| TC-02 | Missing a required field | 422, no candidate row, no file stored |
| TC-03 | Same email twice for one job | 409 `DUPLICATE_SUBMISSION`, still one row |
| TC-04 | Same email on a *different* job | 201 — scoping is per job |
| TC-05 | `.exe` renamed to `.pdf` | 415 on magic bytes (amended from 422) |
| TC-06 | 15 MB file (cap is 5 MB) | 413, upload not fully buffered into memory (amended from 422) |
| TC-07 | 0-byte file | 422 |
| TC-08 | Filename `../../etc/passwd.pdf` | Stored under a generated name; nothing written outside the job folder |
| TC-09 | `field_id` from another template | 422 |
| TC-10 | Storage raises | 500/502, **no candidate row** |
| TC-11 | Submission to a CLOSED job | 410, nothing written |
| TC-12 | Malformed email | 422 |
| TC-13 | Cloud mode | Upload goes through `google_call`, one `api_usage_logs` row |

TC-08 and TC-05 are the ones that matter most — this endpoint is open to the internet.

## Implementation notes

Built as two commits, as suggested above:
1. `feat(US-12): persist candidates and real submission counts` — migration, models,
   and drift row 29's real `GROUP BY` queries. No public-facing behaviour change.
2. `feat(US-12): accept and validate resume uploads on the public apply endpoint` —
   `store_resume`, magic-byte/streaming validation, `candidate_service`, the real
   route, and the full test suite.

Two AC numbers were reconciled against `docs/api-contract.md`, which predates this
story and had already committed to different values: the size cap is **5 MB**, not
10 MB, and file-shape rejections are **413/415**, not 422 (`docs/drift.md` rows 32–33).

`candidates.email`/`.full_name` have no reserved field in a template-driven form —
`app/services/identity_fields.py` resolves them by normalised label match, and
`template_service` now rejects (422 `TEMPLATE_MISSING_IDENTITY_FIELD`) a template
that can't resolve both, at template save time rather than candidate submission time
(`docs/drift.md` row 34).

`POST /public/apply/{slug}` is the one `async def` route in the codebase — solely so
it can `await request.form()` for the field-keyed multipart parts FastAPI already
parsed to resolve `resume: UploadFile`. All blocking work (DB, and in cloud mode
`google_call`'s sleep-based retry) is dispatched via `run_in_threadpool`, since
`google_call` must never run on the event loop.
