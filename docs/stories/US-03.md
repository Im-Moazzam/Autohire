# US-03: Permission recovery — token refresh and reconnect flow

- **Status:** Done — unit-tested against mocked httpx, plus verified end-to-end
  against real Google on 2026-08-11: forced an expired access token (TC-01,
  refresh succeeded, new expiry persisted), forced `invalid_grant` by revoking
  AutoHire's access at myaccount.google.com/permissions (TC-02, `account_state`
  flipped to `REAUTH_REQUIRED`), and reconnected through the real consent screen
  (TC-07/TC-08, `account_state` back to `ACTIVE`, existing refresh token retained
  where Google omitted a new one). Driven by a throwaway scratch script, deleted
  afterward; not part of the committed test suite.
- **Epic:** EP-01
- **Points:** 8
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-01

## Story
As a recruiter whose Google authorisation has expired, I want AutoHire to tell me
clearly and let me reconnect in one click, so that a weekly token expiry doesn't look
like the application is broken.

## Why this is the most important story in EP-01
This story builds `app/adapters/google/session.py` — the wrapper **every** Google call
in the rest of the project goes through. US-06 (Drive folder), US-12 (resume upload),
US-26 (Calendar), and US-27 (Gmail) all sit on top of it. Get it right once here and
those stories inherit refresh, retry, and error handling for free. Get it wrong and
you debug the same class of bug four more times.

Testing-mode refresh tokens expire every 7 days (ADR-002), so this path runs
constantly during development. It is not an edge case.

## The wrapper contract (docs/architecture.md, §Google token handling)
Every call through `session.py` does, in order:

1. Decrypt the recruiter's refresh token
2. Refresh the access token if expired (or expiring within a small skew — use 60s)
3. Make the call
4. On `invalid_grant` → set `account_state = REAUTH_REQUIRED`, raise `ReauthRequired`
5. On 429/5xx → exponential backoff, max 3 attempts
6. Write the `api_usage_logs` row

Rule from architecture.md: `api_usage_logs` is written **by the adapter, never by a
route** — that is what makes every call counted exactly once. Do not add logging calls
in route handlers.

## Acceptance criteria
- [x] `app/adapters/google/session.py` implements the six steps above and is the only
      place a Google access token is refreshed
- [x] A valid-but-expired access token refreshes transparently; the caller never sees it
- [x] A refreshed access token and its new expiry are re-encrypted and persisted —
      not held only in memory
- [x] `invalid_grant` (revoked or 7-day-expired refresh token) sets
      `account_state = REAUTH_REQUIRED` and raises `ReauthRequired`
- [x] The API layer converts `ReauthRequired` to **HTTP 409** with body
      `{"code": "REAUTH_REQUIRED"}` — one exception handler, not per-route try/except
- [x] 429 and 5xx retry with exponential backoff, max 3 attempts, then fail cleanly.
      4xx other than 401/429 does **not** retry.
- [x] One `api_usage_logs` row per outbound call with the correct `api_name`
- [x] `GET /api/v1/auth/google/reconnect` restarts the OAuth consent flow for the
      logged-in recruiter, reusing US-01's state-binding CSRF protection
- [x] A successful reconnect sets `account_state` back to `ACTIVE` and overwrites the
      stored tokens — including the case where Google returns no new refresh token
      (retain the existing one, per US-01's nullable handling)
- [x] Reconnect while already `ACTIVE` is harmless, not an error

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Expired access token, valid refresh | Refreshed silently, call succeeds, new token persisted encrypted |
| TC-02 | `invalid_grant` on refresh | `account_state` → REAUTH_REQUIRED, `ReauthRequired` raised |
| TC-03 | Any route hitting Google while REAUTH_REQUIRED | 409 `{"code": "REAUTH_REQUIRED"}` |
| TC-04 | Google returns 429 twice then 200 | Succeeds after backoff, 3 attempts max |
| TC-05 | Google returns 500 four times | Fails cleanly after 3 attempts, no infinite loop |
| TC-06 | Google returns 403 (not retryable) | Fails immediately, no retry |
| TC-07 | Successful reconnect | `account_state` → ACTIVE, tokens replaced |
| TC-08 | Reconnect where Google omits refresh_token | Existing refresh token retained, not nulled |
| TC-09 | Any successful call | Exactly one `api_usage_logs` row, correct `api_name` |

## Migration
`api_usage_logs` per `docs/schema.md`: `log_id UUID PK`, `recruiter_id UUID FK NULL`,
`api_name api_name_enum`, `call_count INTEGER`, `tokens_used INTEGER NULL`,
`recorded_at`. Append-only — never UPDATE or DELETE. Note: `api_name_enum` in
schema.md still lists `PINECONE`; Pinecone was dropped (`drift.md` row 10) — either
omit that value or leave it unused and say which in the plan.

## Testing approach
There is no real expired token on demand, so drive this with mocked `httpx` responses
for the refresh endpoint (`invalid_grant`, 429, 500, success). One real end-to-end
check is still worth doing once your actual token expires naturally — confirm the
banner appears and reconnect works against real Google.

## Out of scope
The frontend banner itself (Saif — but the 409 contract above is what he builds
against, so it must be exact). Any Drive/Gmail/Calendar *feature* — this story builds
the pipe, not what flows through it. Admin suspension (`SUSPENDED`) is unrelated and
untouched here.
