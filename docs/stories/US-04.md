# US-04: Create and manage application templates

- **Status:** Done
- **Epic:** EP-02
- **Points:** 8
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-02 (done), TS-02 (done)

## Story
As a recruiter, I want to build a reusable application form template with custom
fields, so that every job I launch collects the candidate information I actually need.

## What this story is
The routes and response shapes already exist as stubs from TS-02. This story replaces
the fixtures in `app/api/routes/templates.py` with real persistence. **Do not change
the response shapes** — Saif is building against them. If a shape turns out to be
wrong, that's a `docs/drift.md` row and a regenerated client, not a silent edit.

This is the first real CRUD story. The patterns established here — ownership scoping,
soft delete, nested child writes — get copied by US-06 and everything after it, so
get them right once.

## Acceptance criteria
- [x] Migration creates `form_templates` and `template_fields` per `docs/schema.md`,
      including `field_type_enum`, the partial UNIQUE on
      `(recruiter_id, template_name) WHERE deleted_at IS NULL`, and
      UNIQUE `(template_id, field_order)`
- [x] `POST /templates` creates a template and its fields in **one transaction** —
      a bad field means no template row is left behind
- [x] `GET /templates` returns only the current recruiter's non-deleted templates,
      fields ordered by `field_order`
- [x] `PUT /templates/{id}` (not `PATCH` — ADR-004 P6: aggregate roots owning an
      ordered child collection use `PUT`; `docs/drift.md` row 20) replaces the full
      field set, **reconciled by `field_id`**: a field with an id keeps its row
      (updated in place), one without an id is inserted, and an existing row missing
      from the payload is deleted. This is not a partial update — the client always
      sends the whole array — and it's stronger than blind delete-and-recreate
      because `candidate_form_responses.field_id` is an FK that a wholesale replace
      would orphan later (US-12). State this in the docstring.
- [x] `DELETE /templates/{id}` sets `deleted_at`; the row survives, and the name
      becomes reusable. The 409 `TEMPLATE_IN_USE` response stays declared on the
      route but is **not enforced in this story** — `job_postings` doesn't exist
      until US-06, so there's nothing to check against yet. See `docs/drift.md` row 27.
- [x] `MULTIPLE_CHOICE` and `DROPDOWN` fields require a non-empty `options` array —
      422 otherwise. All other field types must have `options` null.
- [x] `field_order` is normalized server-side to 0..n-1 on write, so the client can
      send any ascending sequence without hitting the UNIQUE constraint
- [x] A template referenced by a job posting cannot be hard-broken — deletion is soft,
      so existing jobs keep resolving their template
- [x] Cross-tenant access returns **404, not 403** (per ADR-004 — don't leak existence)

## Migration
`form_templates` and `template_fields` per `docs/schema.md`. `template_fields` has
`ON DELETE CASCADE` on `template_id` — note this is for hard deletes only; the app
uses soft delete, so cascade is a safety net, not the normal path.

## Out of scope
Template duplication/cloning (US-05, Phase 2). Field-level validation rules beyond
required/options. Any job-posting behaviour (US-06). Frontend — Saif owns it.

## Note
`app/services/template_service.py` is where the logic goes, not the route. The
coverage gate is `app/services` only, so business logic in a route handler is both a
design problem and a CI problem.
