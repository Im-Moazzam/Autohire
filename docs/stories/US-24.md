# US-24: Recruiter availability windows

- **Status:** Done
- **Epic:** EP-05
- **Points:** 5
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-02

## Story
As a recruiter, I want to set the days and hours I'm available for interviews, so that
AutoHire schedules candidates only when I can actually attend.

## What this story is
`GET /scheduling/preferences` and `PUT /scheduling/preferences` exist as TS-02 stubs.
Small, self-contained, and a prerequisite for US-26 — the auto-scheduler has nothing to
place candidates into without it.

## Acceptance criteria
- [x] Migration creates `scheduling_preferences` per `docs/schema.md`, including the
      UNIQUE on `recruiter_id` (1:1) and the CHECK `available_start_time <
      available_end_time`
- [x] `PUT /scheduling/preferences` **upserts** — a recruiter has exactly one row, ever.
      First call creates, subsequent calls update. Never 409 on "already exists".
- [x] `GET` before any `PUT` returns sensible defaults rather than 404 — the frontend
      should render a populated form, not an error state. Say in the plan what the
      defaults are (suggest: Mon–Fri, 09:00–17:00, 30 min) and whether they're persisted
      on first GET or synthesized
      — Defaults are Mon–Fri, 09:00–17:00, 30 min, **synthesized**, never written.
      `SchedulingPreferencesOut.preference_id` is `null` in that case — a read never
      writes a row, so "a row exists" always means "the recruiter set this."
- [x] `available_days` validated against a fixed set of weekday values — reject
      arbitrary strings, and normalize case so `"monday"` and `"MONDAY"` don't both
      persist
- [x] Empty `available_days` → 422. A recruiter with no available days can never be
      scheduled, and US-26 would produce a silent empty result instead of a clear error
- [x] `slot_duration_minutes` bounded (suggest 15–120) and required to divide the
      working window sensibly — a 90-minute slot in a 09:00–10:00 window yields zero
      slots, which should be caught here, not discovered in US-26
      — Bounded 15–120 and required to *fit*, not divide evenly, inside
      `[available_start_time, available_end_time)`. Exact divisibility would reject a
      usable configuration (e.g. 09:00–17:00 at 45 min); "fits" catches the actual
      failure mode (a slot longer than the whole window). Drift row 50.
- [x] Times stored as `TIME` and interpreted in a single, documented timezone. **State
      which and where it's configured.** This is the ambiguity most likely to bite in
      US-26 — a recruiter in Lahore and a UTC server disagree by five hours
      — Single app-wide `SCHEDULING_TIMEZONE` (`app/core/config.py`, default
      `Asia/Karachi`). Not read live: copied onto each row's new `timezone` column at
      insert time and never rewritten by a later update, so a saved row keeps meaning
      what it meant when entered even if the setting changes later. Drift row 48.
- [x] Scoped to the calling recruiter; no `recruiter_id` accepted in the request body

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | First PUT | Row created, 200 with the saved values |
| TC-02 | Second PUT | Same row updated, still exactly one row for that recruiter |
| TC-03 | GET before any PUT | 200 with defaults, not 404 |
| TC-04 | `available_start_time >= available_end_time` | 422, nothing persisted |
| TC-05 | `available_days: []` | 422 |
| TC-06 | `available_days: ["Funday"]` | 422 |
| TC-07 | Mixed case days | Persisted normalized, no duplicates |
| TC-08 | `slot_duration_minutes` larger than the window | 422 with a clear message |
| TC-09 | Body containing `recruiter_id` | Ignored or 422 — never applied |
| TC-10 | Another recruiter's preferences | Unreachable; each recruiter sees only their own |

## Out of scope
`last_synced_at` and any Google Calendar busy-time sync (that's US-25, Phase 2 — this
story is the recruiter's *stated* availability, not their actual calendar). Per-job
overrides. Holidays and blackout dates. Frontend — Saif owns the settings form.

## Note
Keep this story genuinely small. The temptation is to start modelling slot generation
here; that belongs in US-26. This story stores preferences and validates them.
