# TS-07: Cloud cutover — real Drive, Gmail, and Calendar

- **Status:** Done — all five slices complete, Slices 2-4 verified manually
  against real Google Drive/Gmail/Calendar (see `docs/stories/TS-07-summary.md`)
- **Owner:** Moazzam
- **Depends on:** TS-06 merged. Non-negotiable — TS-06 touches the same `APP_ENV`
  branching this story rewrites.
- **Branch:** `feat/TS-07-cloud-cutover`

## Why this exists

`APP_ENV` is a single binary switch driving five adapter factories at once. Today:

- `APP_ENV=local` → real embeddings, **fake** Drive / Calendar / Gmail
  (`LocalCalendarStore` returns `https://meet.local.test/…`)
- `APP_ENV≠local` → real Drive / Calendar / Gmail, but `get_embedder()` **raises
  `NotImplementedError`**, so ranking dies

**There is no configuration in which the whole pipeline runs against real Google
services.** ADR-003 specifies a cutover one service at a time (Drive → Gmail →
Calendar); the current switch makes that impossible — it is all or nothing.

This story replaces the global switch with per-adapter selection and lands the three
Google integrations for real. That is the project's end goal and what the SDS promises.

## Story

As a recruiter, I want AutoHire to store resumes in my Google Drive, put interviews on
my Google Calendar with a real Meet link, and send invitations from my Gmail, so that
the product works against my actual accounts rather than local substitutes.

## Slice 1 — Split the switch

**The problem.** Twelve `settings.app_env` references, of which four are adapter
factories, four are business logic that should not know about environments at all, and
one is a security setting that must stay tied to the deployment, not to which storage
backend is in use:

| File | Line | What it does |
|---|---|---|
| `adapters/resume_store.py` | 119 | factory |
| `adapters/mailer.py` | 51 | factory |
| `adapters/calendar_store.py` | 70 | factory |
| `adapters/embedder.py` | 44 | factory |
| `api/routes/auth.py` | 23 | `_COOKIE_SECURE` — **deployment concern, must stay on `APP_ENV`** |
| `services/job_service.py` | 181 | 500-vs-502 on folder-creation failure |
| `services/candidate_service.py` | 93 | 500-vs-502 on upload failure |
| `services/candidate_service.py` | 231 | whether to persist `resume_storage_key` |
| `services/candidate_service.py` | 325 | which URL `resume_url_for` returns |
| `api/fixtures.py` | 327 | fixture branch |

**Fix.** Add per-adapter settings, defaulting to today's local behaviour so nothing
changes until explicitly opted in:

```
RESUME_STORE=local|drive        # default local
MAILER=local|gmail              # default local
CALENDAR=local|google           # default local
EMBEDDER=fastembed|openai       # default fastembed
```

`APP_ENV` keeps exactly one job: `_COOKIE_SECURE` and other deployment semantics. Each
factory reads its own setting. Then remove `app_env` from business logic entirely:

- **`candidate_service` line 231** — stop asking the environment, ask the returned
  object. `LocalResumeStore` returns `StoredFile(storage_key=<path>)`;
  `DriveResumeStore` returns `StoredFile(storage_key=<id>, drive_file_id=<id>,
  drive_url=<link>)`. So: persist `resume_storage_key` only when
  `stored.drive_file_id is None`. Adapter-agnostic and correct for any future store.
- **`candidate_service` line 325 (`resume_url_for`)** — `if
  candidate.resume_storage_key: return the download route; else: return
  candidate.resume_drive_url`. No environment check.
- **Lines 93 and 181 (500 vs 502)** — the distinction is "our filesystem" vs "an
  upstream service", which is a property of the *store*, not the environment. Either
  key it off `settings.resume_store != "local"`, or (cleaner) have the adapters raise
  distinguishable exception types. Pick one, justify it in the summary.
- **`fixtures.py` line 327** — if TS-06/R-04 left `fixtures.py` with no importers,
  delete the branch or the file; otherwise align it with the new setting.

**Verify first:** re-run the grep and confirm all twelve sites *(verify)*. Then confirm
`_COOKIE_SECURE` behaviour — the review believes modern browsers **do** accept `Secure`
cookies over `http://localhost`, so flipping `APP_ENV` may not break local login, but
this is exactly the kind of thing to check rather than assume *(verify)*.

**Prove it:** tests asserting each factory returns the local implementation by default
and the cloud one when its setting flips; that `resume_url_for` returns the route for a
local `StoredFile` and the Drive link for a remote one, with no `APP_ENV` set either
way.

## Slice 2 — Drive for real

`DriveResumeStore` already exists and is written correctly against raw httpx. What is
needed is to actually exercise it and harden two things.

**Prerequisites (do these by hand, record them in the summary):** Google Cloud project;
Drive, Gmail, and Calendar APIs enabled; OAuth consent screen in **Testing** with your
accounts as test users; `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` /
`GOOGLE_REDIRECT_URI` matching the console exactly. Scopes are already correct in
`adapters/google/oauth.py`: `drive.file`, `gmail.send`, `calendar`, plus the identity
three. `drive.file` grants access only to files the app creates — sufficient here,
because AutoHire creates both the job folder and every resume in it. **Do not widen the
scope set**; ADR-002 notes that adding a restricted scope restarts verification.

**Harden:**
- `DriveResumeStore.store_resume` builds its multipart metadata by f-string
  interpolation: `f'{{"name": "{filename}", "parents": ["{...}"]}}'`. `filename` is
  server-generated (`uuid4` + validated extension) so this is not currently
  exploitable, but it is fragile. Use `json.dumps`.
- Confirm the `webViewLink` returned is openable by the recruiter who owns the token
  *(verify)*.

**Prove it:** existing tests keep passing with `RESUME_STORE=local`. Then a **manual**
run with `RESUME_STORE=drive`: launch a job → confirm the folder appears in Drive →
submit an application → confirm the file lands in that folder → confirm the recruiter
UI's `resume_url` opens it. Paste the observed evidence. Automated tests must continue
to mock the Google layer; do not add a test that needs live credentials.

## Slice 4 — Calendar for real

`GoogleCalendarStore` exists and already passes `conferenceDataVersion=1`, which is
required for a Meet link. Two open questions:

- **`sendUpdates` is not set**, so `events.insert` defaults to `none` and Google will
  **not** email the attendee *(verify)*. This may well be intentional — US-27 sends its
  own invitation via Gmail, and setting `sendUpdates=all` would mean the candidate gets
  two emails. **Make this an explicit decision and record it in an ADR or a drift row.**
  The review's suggestion: leave it at the default and keep AutoHire's own email as the
  single invitation, because that email is the one the product controls, logs, and
  deduplicates. But decide it deliberately rather than by omission.
- `starts_at.isoformat()` is passed without a `timeZone` field. `scheduled_at` is
  UTC-aware so the offset is embedded and this should be correct *(verify against a
  real event's displayed time — this is exactly where a timezone bug would hide, and
  `SCHEDULING_TIMEZONE` is `Asia/Karachi`)*.

**Prove it:** manual run with `CALENDAR=google` — schedule an interview, confirm the
event appears on the recruiter's calendar **at the correct local time**, confirm the
Meet link in the invitation email is a real, joinable link.

## Slice 5 — Embedder: decide, do not default

`get_embedder()` raises `NotImplementedError` for anything but local. The review's
recommendation is to **keep `fastembed` as the production embedder** and mark the
OpenAI path as future work, because:

- `all-MiniLM-L6-v2` is free, deterministic, offline, and already tested
- switching to `text-embedding-3-small` means 1536 dimensions, which means a migration
  altering `ai_analysis_results.embedding` from `vector(384)` to `vector(1536)` **plus
  a full re-embed of every stored vector** — ADR-003 already says so
- `Vector(settings.embedding_dim)` is read at model-import time while the real column
  width is fixed by whichever migration ran. A mismatch is a runtime failure with no
  guard. **If you do build the OpenAI path, add an explicit startup check that the
  configured `EMBEDDING_DIM` matches the actual column width** — this is the single
  most likely way to break ranking silently.
- no marking benefit: the SDS's semantic-matching requirement is satisfied either way

**Fix:** implement `EMBEDDER=openai` **only if you decide the SDS's OpenAI claim must
be literally true.** If you do, it needs the migration, the re-embed path, and the
dimension guard above. If you don't, replace the bare `NotImplementedError` with a
clear message naming `EMBEDDER=fastembed` as the supported value, and record the
decision in `drift.md` (it already has precedent in row 47).

State which way you went and why.

## The blocker nobody has hit yet

**Cloud makes US-03 mandatory.** ADR-002 keeps OAuth in Testing mode, where refresh
tokens expire after 7 days. When that happens, `google_call` raises `ReauthRequired`
→ `409 REAUTH_REQUIRED`. `GET /auth/google/reconnect` exists and works — but
**nothing in the frontend links to it, and nothing handles a 409 `REAUTH_REQUIRED`
response.** Against local fakes this never fires. Against real Google it fires every
week, and the recruiter's only recovery is to clear cookies and sign in again.

This is not optional polish once you are on cloud. At minimum: catch
`REAUTH_REQUIRED` in `frontend/src/lib/http.ts` and surface a "Reconnect Google"
link to `${API_URL}/auth/google/reconnect`. That is small and it is the one piece of
frontend this story may touch. Anything larger belongs to Saif's US-03 work.
