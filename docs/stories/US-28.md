## Story
As a recruiter, I want to cancel an interview slot I can no longer make, so that the
candidate is automatically moved to my next open slot instead of being left hanging.

## Acceptance criteria
- [x] `PATCH /interviews/{slot_id}` with `{"status": "CANCELLED"}` cancels a `PENDING` or
      `CONFIRMED` slot. Any other current status → `409 INVALID_STATE_TRANSITION`
      (mirrors `job_service._LEGAL_TRANSITIONS`)
- [x] Cross-tenant cancel (slot belongs to another recruiter) → `404`, never `403`
      (existing convention — slot simply doesn't exist for this recruiter)
- [x] On cancel, if the slot has a `google_calendar_event_id`, the Calendar event is
      deleted via the `CalendarStore` adapter (new `delete_event` Protocol method, both
      `Local*` and `Google*` implementations). A Calendar failure does not block the
      cancellation — same "never let Calendar block the booking" rule as `calendar_sync.py`
- [x] The system searches for the candidate's next available slot on the same
      recruiter's calendar (reusing `generate_slots`/`occupied_intervals`, same 14-day
      horizon as scheduling). If found: a new `InterviewSlot` row is created (`PENDING`),
      a new Calendar event is created, and the candidate gets an `INTERVIEW_RESCHEDULE`
      email with the new time. The cancelled row stays in history as `CANCELLED`
- [x] If no replacement slot is found in the horizon: the slot is left `CANCELLED` with
      no replacement row, and the candidate gets a `CANCELLATION` email saying the
      recruiter will follow up
- [x] Recruiter can trigger this from the existing interview list
      (`frontend/src/pages/Scheduling.tsx`) — a "Cancel" action per row, confirmed via the
      existing `Modal` component, for rows in `PENDING`/`CONFIRMED` status only
- [x] Both the cancelled row and any replacement row are visible in the interview list
      immediately after the action (no page reload required)

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Cancel a `PENDING` slot, replacement slot available | Old row `CANCELLED`, new `PENDING` row created at next open time, Calendar event deleted+recreated, `INTERVIEW_RESCHEDULE` email logged |
| TC-02 | Cancel a `CONFIRMED` slot, replacement available | Same as TC-01 |
| TC-03 | Cancel with recruiter's calendar fully booked for the horizon | Old row `CANCELLED`, no new row, `CANCELLATION` email logged |
| TC-04 | Cancel an already-`CANCELLED` slot | `409 INVALID_STATE_TRANSITION` |
| TC-05 | Cancel a `DECLINED` slot | `409 INVALID_STATE_TRANSITION` |
| TC-06 | Cancel another recruiter's slot | `404` |
| TC-07 | Calendar adapter raises on delete | Cancellation still succeeds; event id left as-is (not retried) |
| TC-08 | Cancel twice in quick succession (double-click) | Second call sees `CANCELLED` already, 409 — no duplicate replacement slot |

## Notes
Fills in the exact `PATCH /interviews/{slot_id}` contract that's existed as a documented
501 stub since TS-06/R-04 — no new route, no schema change to `InterviewSlotOut`.
`SlotStatus.CANCELLED` and `reschedule_reason` already exist on the model, unused until
now. `EmailType.INTERVIEW_RESCHEDULE` and `EmailType.CANCELLATION` already exist in the
enum, unused until now.

TC-08 has no dedicated test: a second cancel call against an already-`CANCELLED` row hits
the exact same `is_legal_slot_transition` check as TC-04, which already covers "cancel an
already-`CANCELLED` slot → 409" directly — a separate "double-click" test would exercise
identical code.

## Out of scope
Blocking off future availability (blackout dates / time off) — only cancellation of
already-booked interviews. Candidate-driven rescheduling (candidate picks their own new
time) — the system auto-assigns. Bulk/range cancellation — one interview at a time.
