# US-26 + US-27: Auto-schedule interviews and send invitations

- **Status:** Done (backend). Frontend screens are Saif's scope, not started.
- **Epic:** EP-05
- **Points:** 13
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-18/19, US-24

**Implementation notes (read alongside `docs/drift.md` rows 52–58):**
- Routes follow the existing top-level `/interviews` and `/emails` paths (ADR-004
  P2), not the `/jobs/{job_id}/schedule` / `/jobs/{job_id}/slots` /
  `/jobs/{job_id}/emails` paths this story text names — the ADR is binding and
  already matched the pre-existing TS-02 stub contract.
- `docs/schema.md`'s plain `INDEX (recruiter_id, scheduled_at)` became a partial
  UNIQUE (`uq_interview_slots_recruiter_time`) — a plain index enforces nothing,
  and this AC explicitly requires "the index plus a conflict check, not hope."
  The index catches exact-timestamp collisions; a separate interval-overlap
  check in `interview_service.generate_slots` (using each existing slot's own
  stored `duration_minutes`, not the current preference's) catches the case a
  timestamp-only check would miss.
- `intent_detected` is not built (needs a Phase 2 enum); `candidate_reply_text`
  and `reschedule_reason` are present but unused.
- TC-04 reports through a new, additive, nullable `background_tasks.result_summary`
  JSONB column, polled at `GET /tasks/{task_id}` — which this story wired to real
  data for the first time (it was left a TS-02 stub through three prior stories).

> Planned as one story: scheduling a candidate and emailing them about it are one
> user-visible action. **Build as two commits:** (1) slot generation + `interview_slots`,
> (2) email dispatch + `email_logs`.
>
> **This is the last story in Phase 1.** When it lands, the pipeline runs end to end.

## Story
As a recruiter, I want to pick shortlisted candidates and have interviews scheduled and
invitations sent automatically, so that I don't coordinate times by hand.

## Commit 1 — scheduling

### Acceptance criteria
- [x] Migration creates `interview_slots` per `docs/schema.md`, including
      `slot_status_enum`, the **partial UNIQUE on `candidate_id` WHERE status IN
      ('PENDING','CONFIRMED')** (only one live slot per candidate; history is retained),
      and the index on `(recruiter_id, scheduled_at)` for conflict checks
- [x] `POST /jobs/{job_id}/schedule` with `{candidate_ids: [...]}` returns 202 and
      enqueues a `CALENDAR_SYNC` task — same plumbing as `RESUME_PARSE` and
      `BATCH_RANKING`: row on enqueue, own `SessionLocal()`, `acks_late`, and the
      **same widened partial unique index** guarding concurrent runs
- [x] Slots are generated from `scheduling_preferences`: available days, within the
      time window, `slot_duration_minutes` apart, starting from the next available day
- [x] **No double-booking.** Two candidates never get the same `scheduled_at` for one
      recruiter, and an existing PENDING/CONFIRMED slot blocks that time. Enforce with
      the index plus a conflict check, not hope
- [x] Only `RANKED` candidates can be scheduled — 422 otherwise. Scheduling a
      `PARSE_ERROR` candidate is a bug, not a choice
- [x] Candidate moves `RANKED` → `INVITED` (already in `_LEGAL_TRANSITIONS`)
- [x] A Google Calendar event is created via the `CalendarStore` adapter — Protocol +
      local fake + real implementation through `google_call`, exactly the `ResumeStore`
      shape. `google_calendar_event_id` and `google_meet_link` persisted
- [x] **Ordering, as in US-06:** the slot row commits first, *then* the calendar event
      is created, *then* the row updates with the event id. No DB transaction held open
      across a Google call
- [x] Calendar failure leaves the slot row present without an event id and retryable —
      never a candidate marked `INVITED` with no interview
- [x] Requesting more candidates than the available slots in a reasonable horizon →
      schedule what fits and **report the rest explicitly**. Never silently drop
      candidates. State the horizon in the plan (suggest 14 days)

## Commit 2 — invitation email

### Acceptance criteria
- [x] Migration creates `email_logs` per `docs/schema.md`, including the **UNIQUE on
      `idempotency_key`**
- [x] `idempotency_key` is `{candidate_id}:{email_type}:{slot_id or 'none'}` — the
      UNIQUE constraint makes duplicate sends structurally impossible, so retries become
      harmless no-ops. This is the whole design; do not add application-level dedupe on
      top of it
- [x] Email sent via the `Mailer` adapter — Protocol + Mailhog locally + Gmail through
      `google_call`. Same pattern as `ResumeStore` and `CalendarStore`
- [x] `EMAIL_DISPATCH` task, enqueued after the slot is created and its calendar event
      exists — a candidate must never receive an invitation for a slot that failed to
      materialize
- [x] One invitation template covering candidate name, job title, date/time, duration,
      and the Meet link. **One template, not a template system** — that's Phase 2
- [x] `email_logs` row written for every send with the correct `delivery_status`;
      failures recorded, not swallowed
- [x] Email failure does **not** roll back the slot — the interview exists; the email
      is retryable. Surface the failed state rather than deleting the booking
- [x] `GET /jobs/{job_id}/emails` and `GET /jobs/{job_id}/slots` wired to real data,
      retiring the last of `fixtures.CANDIDATES` (`candidate_name()` in `emails.py` /
      `interviews.py`)

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Schedule 3 RANKED candidates | 3 slots, distinct times, all within preferences, all `INVITED` |
| TC-02 | Schedule a `PARSE_ERROR` candidate | 422, no slot |
| TC-03 | Two schedule runs for the same candidate | Still one live slot (partial unique) |
| TC-04 | More candidates than available slots | Scheduled ones succeed; the rest reported explicitly, none silently dropped |
| TC-05 | Calendar adapter raises | Slot row exists without event id, candidate not left `INVITED` with nothing |
| TC-06 | Recruiter with no `scheduling_preferences` | 409 with a clear message, not an empty result |
| TC-07 | Same email sent twice (task retry) | One `email_logs` row, second is a no-op |
| TC-08 | Mailer raises | Slot survives, `delivery_status` records failure, retryable |
| TC-09 | Cross-tenant schedule | 404 |
| TC-10 | Slot times vs preferences | Every slot falls on an available day, inside the window, correct duration |
| TC-11 | Existing PENDING slot at a time | Next candidate gets a different time |

TC-04 and TC-07 are the two that matter most: silent candidate loss and duplicate
emails are both the kind of failure a recruiter discovers from the candidate's side.

## Out of scope

`intent_detected`, `reschedule_reason` columns stay NULL — Phase 2). Reminder emails.
