# TS-14: Admin dashboard (cross-recruiter monitoring + revoke)

- **Status:** Done
- **Owner:** Moazzam (backend + frontend)
- **Depends on:** TS-13, US-01/US-02/US-03
- **Branch:** `feature/TS-14-admin-dashboard`

## Why this exists

The sidebar's "Admin Monitoring" item was a permanently disabled placeholder
(removed in TS-13). Requested directly: a way for the platform operator to see
usage across every recruiter and revoke access for one, without exposing any
of that to normal recruiters. This intentionally crosses the app's normal
tenant-isolation rule (NFR-06/07) — every other route in this codebase scopes
every query by `recruiter_id`; these don't, on purpose, behind a separate
auth boundary.

There was already a half-built hook for the revoke mechanism: `RecruiterState`
has had a `SUSPENDED` value since US-01/US-02, completely unused, with a
`ponytail:` comment in `auth_service.py` marking the exact gap: *"overwrites
SUSPENDED on login since no admin flow exists yet to set it; revisit once the
admin suspend story lands."* This is that story.

## Story

As the platform admin, I want to see per-recruiter usage and account health,
monitor background task failures across everyone, and suspend a recruiter's
access, so I have operational visibility this app never needed when it only
served one team.

## Acceptance criteria

- [x] Single hardcoded admin identity via `ADMIN_EMAIL` env var (no `is_admin`
      DB column, no separate password) — `get_current_admin`
      (`backend/app/api/deps.py`) builds on `get_current_recruiter`, so admin
      access still requires a real Google-authenticated session. Blank
      `ADMIN_EMAIL` disables the dashboard for everyone (403).
- [x] `get_current_recruiter` rejects a `SUSPENDED` recruiter's session with
      401 on every request, not just at login.
- [x] Login no longer resurrects a `SUSPENDED` recruiter back to `ACTIVE`
      (the exact bug the `ponytail:` comment flagged) — regression-tested.
- [x] `GET /api/v1/admin/recruiters` — paginated, per-recruiter usage totals
      (jobs/candidates/interviews/emails) and account health
      (state/created_at/last_login_at). Usage counts verified not to leak
      across recruiters (`test_admin_usage_counts_not_cross_contaminated`).
- [x] `GET /api/v1/admin/tasks` — paginated background task log across every
      recruiter, filterable by status and type.
- [x] `POST /admin/recruiters/{id}/suspend` and `.../reactivate` — an admin
      can't suspend their own account (400 `CANNOT_SUSPEND_SELF`).
- [x] `/admin` frontend route exists but is **not** in `Sidebar.tsx`'s nav
      list — reachable only by typing the URL. Redirects to `/dashboard` on
      a 403 from the backend, rather than rendering a broken admin screen to
      a non-admin.
- [x] `make api-client` run — `frontend/src/lib/api.d.ts` and
      `mobile/lib/api.d.ts` both regenerated and committed.

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Non-admin recruiter hits any `/admin/*` route | 403 |
| TC-02 | `ADMIN_EMAIL` unset | 403 for everyone, including the intended admin |
| TC-03 | Admin lists recruiters | sees every recruiter, own row included |
| TC-04 | Two recruiters with different usage | each row's totals reflect only that recruiter's data |
| TC-05 | Admin tries to suspend their own account | 400 `CANNOT_SUSPEND_SELF` |
| TC-06 | Suspend then reactivate a recruiter | account_state flips SUSPENDED → ACTIVE correctly |
| TC-07 | A suspended recruiter's existing session | 401 on `/auth/me` (and everywhere else) |
| TC-08 | A suspended recruiter logs in again via Google | stays SUSPENDED — does not silently resurrect (regression test for the flagged bug) |

## Notes

No migration — `SUSPENDED` already existed on `recruiter_state_enum`. Usage
totals in `admin_service.list_recruiters` use correlated scalar subqueries
(one bounded query, page size capped at 100 by `PaginationParams`), the same
shape `dashboard_service.get_dashboard_stats` already uses per-recruiter, just
evaluated per-row instead of filtered to one recruiter.

## Out of scope

A UI for granting/revoking *admin* status itself (there's exactly one admin,
set via env var, changed by editing `.env` and restarting — not a feature
worth building for a single operator). Real-time task monitoring (the task
log is a snapshot on page load/filter change, not a live stream — no push
infra exists in this codebase, same reasoning as the dashboard's 30s poll).
