# TS-10: Recruiter dashboard with live stats

- **Status:** Done
- **Owner:** Saif (frontend + backend)
- **Depends on:** US-06, US-13, US-24, US-26-27
- **Branch:** `feat/US-24-26-27-scheduling-emails-frontend`

## Why this exists

Requested directly (not from the RS/SDS baseline, which has no dashboard
use case) once jobs, candidates, scheduling, and emails were all wired to
real data — a landing screen that rolls all four up into one place. Backfills
a story file so it has real acceptance criteria and a DoD, per this project's
convention of not shipping screens without one (see TS-09).

## Story

As a recruiter, I want to land on a dashboard showing live counts across my
jobs, candidates, interviews, and emails, so I can see the state of my
hiring pipeline without opening four separate screens.

## Acceptance criteria

- [x] `GET /api/v1/dashboard/stats` returns recruiter-scoped totals and a
      per-status breakdown for jobs, candidates, interviews, and emails —
      every breakdown zero-filled across its full enum, never omitting a key.
- [x] Candidate counts are scoped through the recruiter's own job postings
      (candidates have no direct `recruiter_id`) and exclude soft-deleted rows.
- [x] Tenant isolation: a second recruiter's data never appears in the
      totals (covered by `test_stats_scoped_to_calling_recruiter_only`).
- [x] Frontend polls `/dashboard/stats` every 30s (`refetchInterval`).
- [x] All five UX states: loading (skeleton), error (retry), empty (zero
      jobs — CTA to post the first job), success, and a real-data view with
      per-card status breakdown chips.
- [x] Charts use only design tokens (`var(--color-x)`) for series colors,
      never raw hex.
- [x] Animations respect `prefers-reduced-motion` (`AnimatedNumber` jumps
      instead of counting up; framer-motion's `useReducedMotion`).

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Recruiter with nothing yet | all totals 0, every breakdown key present at 0 |
| TC-02 | Jobs across every `JobStatus` | `jobs_by_status` counts match, `total_jobs` sums them |
| TC-03 | Candidates across multiple jobs owned by the recruiter | counted across jobs, not just one |
| TC-04 | A soft-deleted candidate | excluded from all counts |
| TC-05 | Interviews and emails belonging to the recruiter | counted correctly by status |
| TC-06 | A second recruiter's jobs/candidates/interviews/emails | never counted in the first recruiter's stats |

## Notes

No schema change — reads existing tables only. `dashboard_service` is the
only place these four `GROUP BY` queries live; no route computes counts
inline. `LocalAnalyzer`/ranking counts are exact matches against
`ai_analysis_results`, not an estimate.

## Out of scope

Historical trends (stats are a point-in-time snapshot, not a time series) —
would need either a periodic snapshot table or an events log, neither of
which exists yet.
