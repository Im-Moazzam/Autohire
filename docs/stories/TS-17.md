# TS-17: Bulk interview scheduling

- **Status:** Done
- **Owner:** Moazzam (frontend) — one backend validation line
- **Depends on:** US-26-27
- **Branch:** `feat/TS-17-bulk-scheduling`

## Why this exists

`POST /interviews` has always accepted a `candidate_ids` array and
`calendar_sync.py` has always looped and reported per-candidate outcomes —
the batch case US-26-27's own AC (TC-04, "more candidates than available
slots") was written for. `Candidates.tsx` never called it with more than one
id (drift row 75): no multi-select, no way to exercise the exact case the
backend was built for.

## Story

As a recruiter, I want to select several ranked candidates and schedule
interviews for all of them in one action, and see a clear summary when some
couldn't be scheduled, so I don't have to click "Schedule interview" once
per candidate.

## Acceptance criteria

- [x] `InterviewCreate.candidate_ids` requires at least one id
      (`Field(min_length=1)`, `backend/app/schemas/scheduling.py`) — an empty
      array is a 422, not a no-op `CALENDAR_SYNC` task.
- [x] New `Checkbox` primitive in `frontend/src/components/ui/`, exported
      from `index.ts` — none existed (design.md's "checkbox selection for
      bulk actions" line had nothing backing it).
- [x] Selection lives on the AI-ranked tab's `RankedCard` grid only, and only
      on `RANKED` candidates — `enqueue_scheduling` requires every selected
      candidate to be `RANKED`, same gate `ScheduleInterviewButton` already
      uses. The checkbox `stopPropagation`s so it doesn't trigger the card's
      `onOpen`.
- [x] A selection bar above the grid when at least one candidate is
      selected: "N selected", a `BulkScheduleButton`, and a "Clear" action.
      Selection is a `Set<string>`, cleared on tab change and when the
      bulk-schedule task reaches a terminal state.
- [x] `BulkScheduleButton` reuses `useScheduleInterviews()` ->
      `useTask()` -> invalidate `["candidates", jobId]` / `["interviews"]`
      -> toast, exactly `ScheduleInterviewButton`'s flow — only the array
      passed to `POST /interviews` and the button copy differ.
- [x] `scheduleOutcome()` (`frontend/src/lib/tasks.ts`) widens to summarise
      a batch: a plural success message when everyone scheduled, the
      original single-reason sentence when exactly one candidate failed
      (unchanged from US-26/27), and a grouped-by-reason-code summary
      otherwise — e.g. "7 scheduled, 2 could not be scheduled: no slot in
      the next 14 days." — covering every reason code `calendar_sync.py`
      emits (`NO_SLOT_IN_HORIZON`, `ALREADY_SCHEDULED`, `SLOT_TIME_TAKEN`,
      `CALENDAR_FAILED`, `NOT_RANKED`, `CANDIDATE_NOT_FOUND`).

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | `POST /interviews` with `candidate_ids: []` | 422 |
| TC-02 | Every selected candidate schedules successfully | Toast: "N interviews scheduled — invites sent." (or the original singular sentence for N=1) |
| TC-03 | Exactly one candidate selected, scheduling fails | The original single-reason sentence (US-26/27 behaviour unchanged) |
| TC-04 | More candidates selected than available slots in the 14-day horizon | Toast reports both the scheduled count and the shortfall reason grouped — the backend's own TC-04 case, never shown in the UI before this story |
| TC-05 | A batch failing for more than one distinct reason | Each reason's count is listed separately, comma-joined |
| TC-06 | All candidates in a batch fail | Toast is an error variant: "Could not schedule N candidates: ..." |
| TC-07 | Nothing selected | "Schedule interviews" action doesn't render (no selection bar) |

## Notes

See `frontend/src/lib/tasks.test.ts` for the full `scheduleOutcome` suite and
`backend/tests/test_interviews.py::test_schedule_interviews_route_empty_array_is_422`
for the backend validation. No migration, no new route — `POST /interviews`
and `calendar_sync_job` were already batch-capable (US-26-27).

Manual browser verification (selecting candidates, seeing the bar appear,
scheduling a batch, checking MailHog for one invite per scheduled candidate)
was not run this session — no browser automation session was available.
Coverage here is the full `tasks.test.ts` suite (unit-level, covers every
`scheduleOutcome` branch) plus a clean `tsc`/`vite` build. Flagging this
explicitly rather than claiming a manual check that didn't happen.

## Out of scope

Selecting across pages (the ranked tab fetches `size=100` in one page
today, drift row 71's existing bound). A "select all" control. Bulk actions
other than scheduling (bulk reject, etc.) — this story is scoped to the one
backend capability that already existed and went unused.
