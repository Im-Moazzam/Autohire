# US-13: Recruiter views raw submissions

- **Status:** Done
- **Epic:** EP-03
- **Points:** 5
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-12

## Story
As a recruiter, I want to see who has applied to a job and open their resume, so that
I can review applications before any AI processing has run.

## What this story is
`GET /jobs/{job_id}/candidates` and `GET /candidates/{candidate_id}` already exist as
TS-02 stubs. `candidates` and `candidate_form_responses` landed in US-12. This story
swaps the fixtures for real queries. Small, but it's the first time a recruiter can
see submitted data — worth having before US-15/16 start transforming it.

No migration.

## Acceptance criteria
- [x] `GET /jobs/{job_id}/candidates` returns the job's non-deleted candidates,
      newest first, scoped to the calling recruiter; 404 for another recruiter's job
- [x] `Page[CandidateOut]` pagination per ADR-004 — no unbounded list
- [x] Optional `submission_status` filter; hits `ix_candidates_job_status`
- [x] Optional `q` filter on name/email (ILIKE), consistent with `list_jobs`
- [x] `GET /candidates/{candidate_id}` returns `CandidateDetailOut` including
      `form_responses` as `{field_label, response_value}` pairs — the label comes from
      `template_fields`, joined, not stored on the response row
- [x] `parse_error` is exposed on both shapes and is null pre-processing
- [x] `resume_url` resolution: Drive `webViewLink` in cloud mode; in local mode a
      **recruiter-authenticated** download route, never a raw filesystem path
- [x] Cross-tenant candidate access → 404 (ADR-004 P8)
- [x] The list endpoint issues a bounded number of queries regardless of page size —
      no N+1 over `form_responses` or template fields

## The resume download route
`GET /api/v1/candidates/{candidate_id}/resume` — authenticated, ownership-scoped,
streams the file from `LOCAL_STORAGE_ROOT`. Needed because `resume_storage_key` is an
absolute server path and must never reach a client.

- Resolve the path and **assert it is inside the job's folder** before opening —
  the stored key is server-generated, but defence in depth, same as US-12
- 404 if the candidate has no stored resume
- In cloud mode this route can redirect to (or simply not exist alongside) the Drive
  `webViewLink`; state which in the plan rather than building both silently
- This route is **not** in the TS-02 contract, so it's an addition — regenerate the
  client and note it in `drift.md`

## Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-01 | Job with 3 candidates | 200, all 3, newest first |
| TC-02 | Another recruiter's job | 404 |
| TC-03 | `submission_status=PARSE_ERROR` filter | Only matching rows |
| TC-04 | Soft-deleted candidate | Excluded from list and 404 on detail |
| TC-05 | Detail response | `form_responses` carry the correct `field_label` per answer |
| TC-06 | Another recruiter's candidate by id | 404 |
| TC-07 | Page size 2 over 5 candidates | Correct `total`, correct page |
| TC-08 | Download another recruiter's candidate resume | 404, file not streamed |
| TC-09 | Candidate with no resume stored | 404 on download |
| TC-10 | List endpoint query count | Bounded — assert with a query counter |

## Out of scope
Triggering AI processing (US-15). Any ranking or scores (US-18/19). Bulk actions,
export, candidate deletion. Frontend — Saif owns the submissions table.
