# US-18 + US-19: Semantic scoring and the ranked shortlist

- **Status:** Done
- **Epic:** EP-04
- **Points:** 13
- **Backend:** Moazzam · **Frontend:** Saif
- **Depends on:** US-15/16

> Planned as one story: US-19 is largely exposure of what US-18 produces.
> **Build as two commits:** (1) embeddings + scoring + `ai_analysis_results`,
> (2) the ranked shortlist endpoint.

## Story
As a recruiter, I want candidates scored against the job description and presented as a
ranked shortlist, so that I can see who fits best without reading every resume — and see
which resumes failed rather than having them silently disappear.

## The rule this story exists to honour
**The score is cosine similarity. The LLM only explains it.**
`architecture.md` is explicit and the reasoning is a viva answer: a deterministic score is
reproducible and defensible; an LLM-produced score cannot be defended and re-runs disagree
with each other. Do not let a model output a number that becomes `semantic_score`.

## Commit 1 — embeddings and scoring

### Acceptance criteria
- [x] Migration creates `ai_analysis_results` per `docs/schema.md`, including the pgvector
      `embedding` column, UNIQUE on `candidate_id`, and an index on `(job_id, rank_position)`
- [x] **Embedding dimension is config-driven** (`EMBEDDING_DIM`, 384 local). Never hardcode
      1536. The migration must read it from settings, not a literal.
- [x] `Embedder` Protocol + `LocalEmbedder` (`all-MiniLM-L6-v2`, 384-dim) behind the adapter
      rule; cloud implementation is not built in this story.
      Built as `FastEmbedEmbedder` (fastembed/ONNX, not sentence-transformers) — same model,
      same 384 dims, no PyTorch in the image. See drift row 45.
- [x] `VectorStore` Protocol with a **pgvector implementation only** — Pinecone is dropped
      (drift row 10). The Protocol exists so the choice is demonstrated, not the integration.
- [x] **Closes drift row 28**: the JD is embedded and `job_postings.jd_embedding_id` is
      populated. US-06 deferred this; it lands here.
      Populated as a `{model}:{dim}:{sha256(jd)[:16]}` provenance ref, not a separate
      `JD_EMBEDDING` task — see drift row 28's updated entry.
- [x] A `BATCH_RANKING` task, enqueued the same way `RESUME_PARSE` is — row written on
      enqueue, own `SessionLocal()`, `acks_late`, scoped `autoretry_for`, and the same
      partial unique index guard against concurrent runs (widened to cover both task
      types — drift row 46)
- [x] Only `PARSED` candidates are scored. `PARSE_ERROR` and `SUBMITTED` are skipped, not
      scored as zero — a failed parse must never rank as a bad candidate.
      `RANKED` candidates are also selected (not just `PARSED`), so a re-run has rows to
      rescore once nothing is `PARSED` anymore — required for TC-03, not a contradiction
      of this AC.
- [x] Cosine similarity between the resume embedding and the JD embedding is the whole of
      `semantic_score`. Store it as returned; do not rescale or round for display
- [x] `rank_position` is assigned 1..n over scored candidates, ties broken deterministically
      (score DESC, then `submitted_at` ASC) so re-runs produce identical ordering
- [x] Candidate moves `PARSED` → `RANKED` (already legal in `_LEGAL_TRANSITIONS`)
- [x] Re-running replaces prior results for that job rather than accumulating duplicates
      (UNIQUE on `candidate_id` forces this — upsert, don't insert-and-hope)
- [x] `matched_skills` / `missing_skills` / `ai_feedback_summary` come from the LLM adapter,
      which is canned/deterministic in local mode (ADR-003). A failure here degrades to NULL
      and **does not fail the candidate** — the score is already computed and is the ranking

## Commit 2 — the ranked shortlist

### Acceptance criteria
- [ ] `GET /jobs/{job_id}/ranking` returns `RankingOut` per the TS-02 contract — shape must
      not change, Saif is building against it.
      **Not built — this AC was a drafting error.** `RankingOut` exists in no generated
      artifact (`docs/openapi.json`, `frontend/src/lib/api.d.ts`, or the TS-02 stubs), and
      ADR-004's Consequences already names "ranked/failed candidates as two lists" as a
      shape to correct (drift row 22, closed). Building it now would reopen a settled ADR
      and break the generated client for no consumer. See drift row 44.
- [ ] **Two separate lists**: `ranked` (scored, ordered by `rank_position`) and `failed`
      (`PARSE_ERROR` candidates with their `parse_error`). Not one list with nullable scores.
      **Not built as one envelope** — same reasoning as above. The two lists exist as two
      real endpoints instead: `GET /jobs/{id}/candidates/ranked` and
      `GET /jobs/{id}/candidates?submission_status=PARSE_ERROR`.
- [x] `/jobs/{id}/candidates/ranked` — the last remaining `fixtures.CANDIDATES` read path —
      is wired to real data or removed. Say which in the plan; do not leave a fixture route
      alongside a real one.
      Wired to real data; shape unchanged (`Page[RankedCandidateOut]`).
- [x] Recruiter-scoped; cross-tenant → 404
- [x] A job never ranked → empty `ranked`, `processed_at` null, and any `PARSE_ERROR`
      candidates still present in `failed`. Not a 404.
- [x] Bounded query count — no N+1 over analysis rows or candidates
- [x] `evidence_snippets` is populated where the LLM provides it but is **not** exposed in
      this story's response (US-23 owns the explainability UI); the column is written, the
      field is not added to `RankedCandidateOut`

### Test cases
| ID | Scenario | Expected |
|---|---|---|
| TC-09 | Job with 4 ranked + 1 failed | `ranked` has 4 in order, `failed` has 1 with its message |
| TC-10 | Job never processed | 200, empty `ranked`, null `processed_at`, not 404 |
| TC-11 | Job with only failures | `ranked` empty, `failed` populated — the shortlist is not an error |

| TC-13 | Query count | Bounded regardless of candidate count |

TC-11 is the partial-failure case `docs/checklists/ux.md` cares most about. If every resume
failed, the recruiter must see *why*, not an empty screen.

## Note on model download
`all-MiniLM-L6-v2` is ~90 MB and downloads on first use. Bake it into the Docker image or
cache the HuggingFace directory in a volume — otherwise CI and every fresh container pay
for it, and an offline machine fails outright.
